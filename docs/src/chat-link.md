# Подключение чата

KAN-7 подключает пользователя к реальному домовому групповому чату MAX и связывает чат с
конкретным домом из локального адресного справочника.

## Выбор дома

Есть четыре способа, как в исходном меню:

1. **Выбрать место жительства** — бот: город → район → улица → дом.
2. **Указать почтовый индекс** — бот: индекс → улица → дом (без повторного выбора города/района).
3. **Указать на карте** — WebApp (`chat_link_map`), ближайшие дома по курсору.
4. **Ввести текстом** — WebApp (`chat_link_text`), быстрый fuzzy-поиск адреса.

Поиск по индексу внутри WebApp не показывается. Текстовый WebApp содержит одно поле адреса.
После выбора дома система проверяет, подключён ли к адресу групповой чат MAX и состоит ли
пользователь в нём. Если членство подтверждено через MAX, адрес сохраняется и бот присылает
отдельную главную с фото. Иначе сохранения и персональной ленты нет: человеку рекомендуют
вступить в чат через «Госуслуги Дом» либо показывают приглашение администратору.

Все способы заканчиваются одним `address_id`, после чего используется один и тот же flow
подключения чата.

### Адреса только из памяти

KAN-7 не создаёт второй справочник. Он переиспользует существующий `address.StreetCatalog`,
который уже нужен парсерам для in-memory street lookup. Для onboarding каталог один раз загружается
с `city=None` и хранится process-wide; после прогрева callback-и и API поиска/карты не делают
`SELECT` для построения кнопок. БД используется для первоначального snapshot и persistence
выбранного дома/чата.

`StreetCatalog` хранит структурированные `city / district / street / house`, координаты,
почтовый индекс и `address_id`. UI нормализует NFKC, регистр, `ё/е`, пробелы и zero-width Unicode;
одинаковые варианты не дублируются.

### Район и пагинация

Основной UX первого способа всегда идёт через район, а не через «слоги» улицы. Район берётся из
локального адресного snapshot; карта в MiniApp отображается через Yandex Maps JS API, а ближайшие
дома по-прежнему ищутся в `StreetCatalog`, поэтому движение карты не делает внешний геокодинг на
каждый жест пользователя.

Обычные списки picker-а ограничены 10 предметными кнопками на страницу, чтобы клавиатура не
становилась слишком высокой. Номера домов идут по 15 на страницу — ровно 5 рядов по 3 кнопки.
Навигация везде одинаковая: `‹  1 / N  ›` и отдельная кнопка `← Назад`; если страниц больше 10,
добавляются переходы `«5` и `5»`. Только если даже
после выбора района улиц всё ещё аномально много (>72), появляется дополнительное
prefix-сужение; оно использует ту же пагинацию и не является штатным шагом flow.

Почтовый индекс — самостоятельный фильтр области поиска. После ввода индекса picker **не спрашивает
ни город, ни район**: пользователь сразу получает улицы внутри этого индекса, затем дома:
`индекс → улица → дом`. Если одинаковый номер дома встречается у нескольких адресов внутри одного
индекса и улицы, кнопка добавляет locality только для различения вариантов.

## Один bot-screen

Весь личный onboarding живёт одним сообщением бота. Callback-переходы используют edit, а не
`send → delete`. `flow_mid` хранится в FSM, поэтому после обычного текстового сообщения с индексом
редактируется тот же экран. Повторный `/start` сбрасывает незавершённый state и переиспользует
этот экран, если сообщение ещё существует.

## Реальный групповой MAX-чат

После выбора дома создаётся `chat_links` — явная state machine заявки. Отдельная сущность нужна,
потому что между выбором дома и появлением реального MAX `chat_id` есть незавершённый lifecycle.
`chats` и `users_chat` по-прежнему принадлежат модулю `user_chat`.

### Домовой чат уже подключён

Пользователь не добавляется в чужую группу автоматически. Если у выбранного дома есть подключённый
MAX-чат, но пользователь в нём не состоит, бот рекомендует вступить через «Госуслуги Дом».
После фактического вступления событие `user_added` идемпотентно создаёт `users_chat`;
`user_removed` удаляет членство. Выбор адреса повторно проверяет MAX API, поэтому одна ссылка
или устаревшая запись в БД не подтверждает членство. Legacy DIALOG-записи старого mock-flow не
открывают доступ.

### Домового чата ещё нет

Для администратора основной flow начинается с уже созданной MAX-группы:

1. администратор добавляет бота в групповой чат;
2. бот сразу публикует кнопку **«Выбрать адрес»** и напоминает выдать право
   `read_all_messages`;
3. кнопка открывает личный диалог через `chat_bind_<chat_id>`;
4. пользователь выбирает конкретный дом через бот или мини-приложение;
5. перед привязкой сервис проверяет admin/owner, право бота `read_all_messages`, отсутствие уже
   подключённого адреса у этого MAX-чата и отсутствие другого активного домового чата у
   выбранного адреса;
6. только после этих проверок сохраняются `chat_id`, `address_id` и membership администратора.

Для карты и текстового ввода целевой `chat_id` входит в WebApp start-param, поэтому тот же flow
работает не только в нативном picker-е бота. Если адрес уже занят другим домовым чатом, привязка
не создаётся и администратору предлагается выбрать другой дом.

Старый сценарий остаётся обратно совместимым: если пользователь сначала выбрал адрес и уже имеет
`waiting_group`, событие `bot_added` по-прежнему может автоматически завершить такую заявку после
выдачи прав. Однако предварительный выбор адреса больше не является обязательным.

Обычный resident-flow после выбора дома не меняется: житель может скопировать deep-link для
администратора, а кнопка `Я администратор чата` показывает инструкцию по добавлению бота.

После подключения бот публикует в рабочем чате welcome и referral deep-link `chat_<chat_id>`.
Deep-link не является доказательством членства: при открытии бот сначала проверяет через MAX, что
пользователь действительно состоит в этой группе, и только затем создаёт `users_chat`. Поэтому
ссылку можно безопасно использовать для быстрого онбординга соседей.

В личном welcome кнопка `Смотреть события` скрыта, пока у пользователя нет ни одного реального
membership.

## Первый вход, личный адрес и групповое сообщение

Презентационный текст с именной обложкой отправляется только при первом создании пользователя.
Следующий экран выбора дома использует изображение летящего голубя, главная — голубя в квартире.
Если адрес уже выбран и соответствующее членство подтверждено, повторный `/start` ведёт сразу
на главную, без повторной презентации. Для пользователя без адреса выбор доступен всеми четырьмя
способами, но сам ввод адреса не даёт доступа к ленте.

- **Есть подключённый чат, но человек не участник:** рекомендация вступить через
  «Госуслуги Дом» и повторить выбор.
- **Нет подключённого чата:** кнопка копирования приглашения для администратора,
  «Я администратор» открывает инструкцию по подключению чата/бота. До подтверждённого
  членства личный адрес не сохраняется.
- **Членство подтверждено через MAX для выбранного адреса:** сохраняется
  `users.address_id` и `users_chat.address_id`, открывается главная и nearby.

В групповом чате бот сохраняет `chats.welcome_mid` и редактирует одно сообщение со всем
списком `chat_addresses` при добавлении или удалении дома администратором. Для удаления
доступна кнопка в группе и защищённый API; последний адрес нельзя удалить, пока группа
остаётся подключённой. У ранее созданных сообщений без сохранённого `mid` первое обновление
создаст новое отслеживаемое сообщение, последующие будут редактировать именно его.
Новая миграция: `0023_group_welcome_message` (после `0022_user_residence`).
