# Подключение чата

KAN-7 подключает пользователя к реальному домовому групповому чату MAX и связывает чат с
конкретным домом из локального адресного справочника.

## Выбор дома

Есть четыре способа:

1. **Выбрать место жительства** — полностью в боте: `город → район/местность → улица → дом`.
2. **Указать почтовый индекс** — в боте. Индекс только сужает тот же picker и никогда не
   считается выбранным домом.
3. **Указать на карте** — WebApp (`start_param=chat_link_map`). Геопозиция пользователя — только
   старт карты: курсор можно передвинуть к дому. Backend возвращает ближайшие дома из локального
   справочника в радиусе 1.5 км от курсора.
4. **Ввести текстом** — WebApp (`start_param=chat_link_text`). Это менее заметный последний
   вариант; используется fuzzy-поиск полного адреса, после которого пользователь подтверждает
   конкретный дом.

Все способы заканчиваются одним `address_id`, после чего используется один и тот же flow
подключения чата.

### Адреса только из памяти

KAN-7 не создаёт второй справочник. Он переиспользует существующий `address.StreetCatalog`,
который уже нужен парсерам для in-memory street lookup. Для onboarding каталог один раз загружается
с `city=None` и хранится process-wide; после прогрева callback-и и API поиска/карты не делают
`SELECT` для построения кнопок. БД используется для первоначального snapshot и persistence
выбранного дома/чата.

`StreetCatalog` хранит структурированные `city / district / street / house`, координаты,
почтовый индекс и `address_id`. UI нормализует NFKC, регистр, `ё/е`, пробелы и zero-width Unicode;
одинаковые варианты не дублируются.

### Район и пагинация

Основной UX первого способа всегда идёт через район, а не через «слоги» улицы. Для Москвы
район определяется по координатам дома и административным границам OpenStreetMap
`boundary=administrative + admin_level=8`. Это позволяет получать именно муниципальные районы
вроде `Ростокино`, а не случайные locality из `addr:suburb/addr:place`. Старые подписи locality
используются только как fallback после очистки служебных значений (`Moscow`, `Город не указан`,
названия ЖК/дорог и т. п.). Если район действительно неизвестен, остаётся `Район не указан`.

Размер страницы считается от числа вариантов. Для небольших списков показываются все варианты;
для больших picker стремится держать примерно до шести страниц и 6–12 предметных кнопок на
экране. Обычные `← / →` перелистывают соседние страницы. `-5 / +5` добавляются только при 10+
страницах. Только если даже после выбора района улиц всё ещё аномально много (>72), появляется
дополнительное prefix-сужение; оно может углубляться повторно и не является штатным шагом flow.
Короткие номера домов размещаются сеткой в 2–3 колонки; длинные подписи автоматически возвращают
одну колонку. Для домов допустимо до 18 кнопок на странице, чтобы не получать десятки страниц.

Почтовый индекс — самостоятельный фильтр области поиска. После ввода индекса picker **не спрашивает
ни город, ни район**: пользователь сразу получает улицы внутри этого индекса, затем дома:
`индекс → улица → дом`. Если одинаковый номер дома встречается у нескольких адресов внутри одного
индекса и улицы, кнопка добавляет locality только для различения вариантов.

## Один bot-screen

Весь личный onboarding живёт одним сообщением бота. Callback-переходы используют edit, а не
`send → delete`. `flow_mid` хранится в FSM, поэтому после обычного текстового сообщения с индексом
редактируется тот же экран. Повторный `/start` сбрасывает незавершённый state и переиспользует
этот экран, если сообщение ещё существует.

## Реальный групповой MAX-чат

После выбора дома создаётся `chat_links` — явная state machine заявки. Отдельная сущность нужна,
потому что между выбором дома и появлением реального MAX `chat_id` есть незавершённый lifecycle.
`chats` и `users_chat` по-прежнему принадлежат модулю `user_chat`.

### Домовой чат уже подключён

Пользователь не добавляется в чужую группу автоматически. Для адреса показываются только реальные
групповые MAX-чаты и, если доступно, обычная invite link. После фактического вступления событие
`user_added` идемпотентно создаёт `users_chat`. Legacy DIALOG-записи старого mock-flow не
показываются и не дают доступ к событиям.

### Домового чата ещё нет

Заявка получает статус `waiting_group` и capability-token.

- Если инициатор администратор, он добавляет бота в свой групповой чат и назначает его
  администратором с правом `read_all_messages`. На `bot_added` сервис запоминает пользователя,
  добавившего бота, и ждёт выдачи прав. После подтверждения прав MAX группа связывается с домом
  автоматически, без отдельной команды в групповом чате.
- Если инициатор не администратор, он пересылает админу сообщение/deep-link. Открытие
  `chat_admin_<token>` отмечает, какой пользователь взял заявку; это ещё не даёт прав. Когда бот
  появляется в группе, MAX admin/owner проверяется заново.

`/connect` в пользовательском flow не используется. Если права боту не выданы в течение окна
ожидания, сервис просит проверить admin + `read_all_messages` и повторно добавить бота.

После проверки admin/owner сохраняются реальный `chat_id`, название, invite link, `address_id` и
membership администратора. Если заявку создавал другой пользователь, он вступает в группу обычным
способом; бот не вызывает auto-add участников.

После подключения бот публикует в рабочем чате welcome и referral deep-link `chat_<chat_id>`.
Deep-link не является доказательством членства: при открытии бот сначала проверяет через MAX, что
пользователь действительно состоит в этой группе, и только затем создаёт `users_chat`. Поэтому
ссылку можно безопасно использовать для быстрого онбординга соседей.

В личном welcome кнопка `Смотреть события` скрыта, пока у пользователя нет ни одного реального
membership.
