# Подключение домового чата (KAN-7)

`chat_link` — один модуль фичи onboarding: выбор дома, состояние заявки и оркестрация реального
группового MAX-чата. Сам чат и membership хранятся в `user_chat`; адресный snapshot и поиск — в
существующем `address.StreetCatalog`.

Слои соответствуют корневому `AGENTS.md`:

- `models/` — состояния/результаты без ORM;
- `db/` — только `ChatLinkRow`;
- `handlers/` — address cache и бизнес-логика заявки/группы;
- `api/` — тонкие endpoints WebApp;
- `commands/` — MAX/FSM и редактирование bot-screen.

## Выбор адреса

Вернули четыре видимых варианта исходного меню:

1. `Выбрать адрес` — бот: город → район → улица → дом.
2. `Указать почтовый индекс` — бот: индекс → улица → дом.
3. `Указать на карте` — WebApp `chat_link_map`.
4. `Ввести текстом` — WebApp `chat_link_text`, только быстрый текстовый fuzzy-поиск.

Каждый успешный выбор отправляет пользователю отдельную главную с фотографией.
Обычный выбор доступен только участнику подключённого домового чата после
проверки MAX. Личный дом сохраняется в `users.address_id` независимо от списка
адресов группы. Если дом входит в `chat_addresses`, он также сохраняется как
адрес членства в `users_chat`. Посторонний получает
приветствие и инструкцию вступить в чат, без возможности выбрать дом.
Повторный `/start` с выбранным домом открывает главную.
«Управлять адресами» — заглушка (отдельная задача).

Все ветки дают `address_id`: администратор добавляет его в `chat_addresses`,
а житель выбирает свой дом среди адресов подключённого чата.

## Переиспользование address in-memory

Нового параллельного address cache нет. `handlers/cache.py` держит process-wide экземпляр
`StreetCatalog.load(session, city=None)`. Этот же класс уже используется parser-модулями для
street lookup; для KAN-7 он расширен структурированными публичными домами, postal, координатами,
fuzzy address search и nearest lookup.

Snapshot прогревается при старте bot до polling. Из него один раз строятся индексы
`город → район → улица → дом`, postal lookup, prefix-buckets для autocomplete и geo-grid для
карты. Поэтому ни одна кнопка `город/район/улица/дом`, текстовая подсказка или движение карты
не делает SQL и не сканирует всю таблицу `addresses` заново. SQL остаётся только там, где надо
сохранить/прочитать состояние заявки или чата. Тесты `test_cache.py` и
`test_address_catalog.py` это защищают.

## Picker и количество кнопок

Варианты нормализуются NFKC/casefold, `ё → е`, zero-width/control мусор удаляется, UI-дубли
объединяются. Порядок дома natural (`2`, `3`, `10`).

Обычные списки picker-а показывают максимум 10 предметных кнопок на страницу. Номера домов
показываются по 15 — 5 рядов по 3 кнопки, без одинокой растянутой кнопки на каждой полной странице.
Навигация всегда выглядит одинаково: `‹  1 / N  ›`, затем `← Назад`; если страниц больше 10,
появляются быстрые переходы `«5` и `5»`. Нормальный flow не показывает выбор «по буквам»: prefix-сужение
появляется только как аварийный подэтап, если после района остаётся >72 улиц, и может углубляться
повторно.

## Реальная MAX group integration

### Чат уже есть

Для выбранного `address_id` показываются только подтверждённые групповые MAX-чаты. Старые
KAN-7 mock-записи с DIALOG `chat_id` не считаются домовыми чатами. Пользователь не добавляется
в группу через API: если у группы есть invite link, onboarding показывает обычную link-кнопку.
После фактического вступления update `user_added` сохраняет `users_chat` идемпотентно.

### Чата ещё нет

Основной admin-flow теперь начинается **с группового чата**, а не с заранее выбранного адреса:

1. администратор добавляет бота в MAX-группу;
2. бот публикует в группе кнопку `Выбрать адрес`;
3. deep-link `chat_bind_<chat_id>` открывает личный диалог с ботом и сохраняет целевой `chat_id`
   в FSM;
4. адрес выбирается одним из способов; для WebApp `chat_id` передаётся в start-param и
   затем в `POST /chat-link/select`;
5. перед записью сервис заново проверяет, что пользователь — admin/owner этой группы, бот имеет
   `read_all_messages`, а у выбранного адреса нет другого активного домового чата;
6. после успешной проверки создаётся `chat_links`, реальный `chats` и membership администратора.

`chat_links` по-прежнему хранит lifecycle (`waiting_group`, `waiting_join`, `connected`,
`cancelled`) и capability-token. Старый сценарий «сначала выбрать адрес, затем добавить бота»
оставлен совместимым: если на `bot_added` у пользователя уже есть `waiting_group`, фоновая
автопривязка завершит её как раньше. Но предварительный выбор адреса больше не требуется.

Resident-flow после выбора дома тоже сохранён: обычный житель может передать администратору
скрытую deep-link, а `Я администратор чата` показывает старую инструкцию. Открытие
`chat_admin_<token>` закрепляет такую заявку за администратором; его admin/owner всё равно
проверяется через MAX перед финальной привязкой.

После подключения бот публикует в группе только кнопку «Указать свой адрес» с referral
`chat_<chat_id>`: пользователь переходит в личку; после проверки членства через MAX все адреса
группы сохраняются в личный список. При единственном адресе он становится выбранным домом,
при нескольких пользователь отдельно указывает свой дом для персональных новостей.
Такая же ссылка вставляется в `#итого` группы.
Настройка и добавление адресов администратором выполняются в личном чате с ботом. Команды
`/start`, `/home` и `/get_notify` из группы не обрабатываются; прежняя групповая `/address`
убрана. Повторно добавлять бота в MAX-чат для следующего адреса не нужно.
После сохранения адреса через клавиатуру бота есть кнопка `Добавить ещё адрес`, которая
сохраняет выбранный `target_chat_id` и возвращает к выбору следующего дома.
Открывшему referral соседу подтверждаем реальное членство через MAX и сохраняем все
адреса чата в `user_chat_addresses`. Персональный дом (`users_chat.address_id`) по-прежнему
один: при единственном доме он выбирается автоматически, при нескольких житель выбирает
свой дом самостоятельно — не назначаем случайный адрес для ленты рядом.
Старый `chats.address_id` остаётся первым адресом для совместимости; полный список хранится в
`chat_addresses`.

Событие MAX `bot_removed` открепляет группу от сервиса: `chat_type` становится `removed`,
invite link очищается, а локальные `users_chat` для этого чата удаляются. Поэтому удалённый бот
сразу перестаёт давать дому статус подключённого чата; повторное добавление идёт через обычный
onboarding.

В `chats.chat_type` значение `chat` означает подтверждённую группу. `NULL` оставлен для legacy
записей до реальной group integration и не открывает пользователю раздел событий.

## Один экран

Callback-и редактируют исходное сообщение. `flow_mid` хранится в FSM для текстового ввода индекса.
`/start` очищает незавершённый flow и старается переиспользовать текущий screen. Events в welcome
появляются только после подтверждённого членства и выбора собственного адреса.

Подробное пользовательское описание: `docs/src/chat-link.md`.

## Сценарии адреса и актуальное сообщение группы

При первом `/start` отправляются приветственный текст с именем и обложка `assets/first_start.webp`;
при следующих запусках участник с выбранным адресом видит главную `assets/home.webp`, а человек без
адреса — выбор одного из четырёх способов с `assets/other_messages.webp`.

Любой может выбрать дом, но сохранение личного адреса и nearby требуют реального членства в
подключённом к этому **конкретному дому** MAX-чате. Для чужого подключённого чата выдаётся
рекомендация вступить через «Госуслуги Дом». Если чат не подключён, выдаётся приглашение
администратору или инструкция через кнопку «Я администратор». Локальная запись membership
не подменяет свежую проверку MAX при выборе; `user_removed` убирает её при выходе.

Групповой анонс включает **все** подтверждённые админом дома. ID сообщения хранится в
`chats.welcome_mid` (миграция `0023_group_welcome_message`), и при добавлении или удалении адреса
сообщение редактируется. Администратору доступна кнопка удаления в чате или API DELETE
`/chat-link/groups/{chat_id}/addresses/{address_id}`. Последний адрес удалить нельзя.
Для групп, подключённых до миграции без сохранённого ID, первое обновление создаёт
отслеживаемый анонс; дальнейшие обновления редактируют его.

## Изображения сообщений

- Новому пользователю логотипная обложка приходит только с первым приветствием. Признак нового
  пользователя берётся из первой записи `users`, а не из каждого `/start`; существующим пользователям
  обложка повторно не отправляется.
- Во всех остальных сообщениях, включая переходы по кнопкам, — обложка с летящим голубем.
  Главная сохраняет собственную обложку; дополнительный `address_id` на это не влияет.
- Первый анонс группового чата содержит логотипную обложку; список адресов дальше обновляется
  редактированием того же сообщения без новых анонсов.
